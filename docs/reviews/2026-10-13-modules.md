## P2：模块预检失败仍推进 BK7 批次

位置：`public/app.js:504`、`:505`、`:1074`。
`importSelectedBk7` 调用异步 `openModuleImport` 后立即推进 offset，不等待预检；后者 catch 只展示错误且不返回成功状态。
多于 48 项时，网络错误、规则源错误或大小超限会跳过本批，下一次点击从下一批开始。处理中按钮仍可点击，也允许重复/并发请求。
证据：直接调用路径；本次没有执行实际 App 跳转。线上已有合法 BK7 选择触发大小错误，见下一项。
建议：异步等待并区分成功/失败，仅成功交接时推进；预检期间禁用同一批操作，失败保留原批次。App 实际导入成功仍不能由 Hub 判断。

## P2：合法大规则选择没有可继续的模块拆分路径

位置：`public/lib/module-package.mjs:47`、`public/app.js:500`。
当前批次只按文件数量 48 拆分，不按模块编码后的 900000 字节上限。一个或两个大 BK7 文件就能超限；用户得到内部字节错误，但界面未指出具体文件或提供按大小拆分/旧入口指引。
线上复现：选择 `rules/all/AdGuardSDNSFilter/AdGuardSDNSFilter_All_01.arrs` 和 `.../AdGuardSDNSFilter_All_02.arrs`，`/api/modules/selection.amod?paths=...` 返回 400：`Module JSON exceeds 900000 bytes: 4470978`。
上限校验本身应保留；问题是合法选择不能完成模块路径且没有恢复方案。单文件是否也超限本次未验证。
建议：先按大小规划模块批次，单文件超限明确提示需拆规则或使用兼容入口；不要放宽 App 的同步负载上限。

## 其他优化与验证边界

普通模块每次预检/刷新都读取 catalog 与源文件，ETag 在抓取和包装之后计算；客户端 304 不省源读取和包装成本。可考虑有界、短 TTL 的服务端缓存，但必须保持上游更新可见，不能沿用开屏静态包的发布假设。
普通模块只取 catalog.icon 为 icon-light；没有独立暗色图标传递。属于完整性优化，未证明当前上游需要双图标。
模块 API 单测已加入 `npm test`，但前端失败批次、pending 状态、关注版本隔离、长驻刷新没有覆盖。现有解析模型测试不是 Swift 实机解析对照测试。
